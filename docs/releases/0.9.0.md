# AllotForge 0.9.0 development prerelease

## Added

- A repeatable, explicitly scoped Kubernetes/Kueue component acceptance suite for a dedicated disposable CPU-only kind cluster. It uses actual AllotForge-generated queue resources and a real Kueue controller to exercise activation, CPU quota reservation, a quota-blocked workload, reservation handoff and owned-fixture cleanup. Standalone Workload objects do not create workload Pods or Jobs.
- A pinned compatibility profile: kind v0.33.0, Kubernetes v1.34.11 and Kueue v0.20.5/v1beta2. Official manifest bytes are hashed before parsing, and the controller image is pinned to the verified OCI index digest before installation.
- Private immutable target credentials, explicit instance identity, bounded calls/responses/subprocesses, absent-target prechecks, UID/resourceVersion delete preconditions and sanitized non-overwriting evidence files.
- A read-only-permission, exact-source CI gate with a standard runner, capped duration, explicit cluster teardown and only the sanitized report uploaded. The existing prerelease build now also depends on this component gate.
- A compatibility/evidence matrix identifying the beta1 removal and Kubernetes support floor in Kueue 0.20. The older Ray beta1 queue bundle is explicitly incompatible with that target; it is not silently rewritten.

## Scope and evidence

The fixture pool/policy metadata and protected selector are synthetic and are never applied as real managed resources or Node labels. GPU quota is zero. Positive AllotForge operator reconciliation still needs actual whole-GPU inventory and remains unverified. No fake GPU Nodes, GPU sessions, driver/device-plugin changes, paid runners or cloud clusters are introduced.

A passing report means only its bounded CPU generated-resource cases and cleanup passed for the exact recorded source and pins. It does not certify workload execution, GPU placement, hardware isolation, tenant RBAC, Lease failover, native admission on the new target, OpenShift, KubeRay, production readiness, performance or savings. Existing native-admission checks run separately. Report content is not independent attestation.

The runner is source-checkout tooling rather than an application-wheel feature. No UI behavior or runtime application API is changed. See [acceptance instructions](../cluster-acceptance.md) and [compatibility matrix](../compatibility-matrix.md). Remote outcomes belong to their exact GitHub Actions run and artifact; preparation or synthetic tests alone are not runtime acceptance.
